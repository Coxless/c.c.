1. 全体の流れ

.c.c を C++23 に変換し、あとは普通の C++ コンパイラ（g++ 13 以降）でビルドします。C.C. 独自の価値（契約・スキーマ・効果）はすべてトランスパイラ側にあり、生成コードはランタイムヘッダー1本に依存するだけです。

2. ステップ0：ランタイム cc.hpp

トランスパイラを書く前に、生成コードの完成形を examples/hand/ に手で書き、それが使う部品を cc.hpp にまとめました。トランスパイラはこの手書き版と同じ形の C++ を出すように作っています。

部品内容
RefineError条件付きの型の条件が破れた。型名と、.c.c に書いた条件の文字列を持つ
FieldError / ParseErrorスキーマの parse で壊れていたフィールドを全件、パス（tags[1]、address.city）付きで保持
Raw<T>未検証の外部入力。T への変換手段がないので、parse を通さずに使うと C++ でもエラーになる
violation()契約違反レポート。責任（呼び出し側／実装側）、条件、位置、関係する値を表示。enforce（停止）/ observe（報告して続行）/ off
decode<T> / refine_into<S> / encodeJSON と生成型の相互変換。条件付き型・スキーマ・vector・optional を型で振り分ける
run_mainmain を包み、? などで送出された例外を「エラー: ...」と表示して終了コード 1 にする
組み込み関数len trim email_format parse_json（純粋）、print（io）、log（log）、read_file（io, throw）

完了条件の3つ（Port::of<0>() がコンパイルエラーになる、壊れたフィールドが全件報告される、残高不足で「責任: 呼び出し側」と出る）は cargo test の hand 系テストで確認しています。

3. ステップ1：条件付きの型

type 宣言1行が、検査付きの薄いラッパークラスになります。コンストラクタは private なので、値を作る方法は try_from（実行時に検査、std::expected を返す）と of<V>()（リテラル用、requires でコンパイル時に検査）の2つだけです。

入力 examples/port.c.c

type Port = u16 where 1 <= self <= 65535;

出力 tests/snapshot/port.cpp

class Port {
 public:
  using underlying_type = std::uint16_t;
  static constexpr bool check(const std::uint16_t& self) { return 1 <= self && self <= 65535; }
  static constexpr std::expected<Port, ::cc::RefineError> try_from(std::uint16_t v) {
    if (!check(v)) return std::unexpected(::cc::RefineError{"Port", "1 <= self <= 65535"});
    return Port(std::move(v));
  }
  // Literals: checked at compile time, no runtime check left.
  template <std::uint16_t V>
    requires(check(V))
  static consteval Port of() { return Port(V); }
  constexpr const std::uint16_t& get() const { return v_; }
  constexpr operator const std::uint16_t&() const { return v_; }
  friend constexpr bool operator==(const Port&, const Port&) = default;
 private:
  explicit constexpr Port(std::uint16_t v) : v_(std::move(v)) {}
  std::uint16_t v_;
};

リテラルを条件付きの型に入れると of<V>() に変換されるため、実行時のチェックは残りません。型の分からない値から暗黙に変換しようとすると、トランスパイル時にエラーになります（5章）。

使う側

fn main() effects(io) {
  let http: Port = 8080;
  print("literal:", http);
  print("try_from(443):", Port::try_from(443));
  print("try_from(0):", Port::try_from(0));
}

実行結果

literal: 8080
try_from(443): ok(443)
try_from(0): err(Port の条件 1 <= self <= 65535 を満たしていません)

元の型への暗黙変換（operator const T&）を持たせているので、読むときは普通の値として比較・計算・表示できます。

4. ステップ2：関数の契約と責任

contract fn の pre / post は、関数の入口と return の直前で行う実行時チェックになります。

入力 examples/withdraw.c.c

contract fn withdraw(Account& a, i64 amt) -> i64
  effects(log)
  pre(amt > 0, "金額は正")
  pre(a.balance >= amt, "残高が足りる")
  post(r: r == amt)
  post(a.balance == old(a.balance) - amt)
{
  a.balance -= amt;
  log("withdraw", amt);
  return amt;
}

変換の要点

  • pre：関数の先頭で検査し、破れていれば Blame::caller（呼び出し側の責任）で報告します。
  • old(x)：pre の後で const auto cc_old_N = x; としてコピーを取り、post ではそのコピーと比べます。
  • post：ラムダ cc_post にまとめ、すべての return を「値を一度変数に入れる → cc_post を呼ぶ → 返す」に書き換えます。破れていれば Blame::callee（実装側の責任）です。
  • 呼び出し位置：契約付きの関数には隠し引数 std::source_location cc_caller = std::source_location::current() を付けます。既定引数は呼び出し側で評価されるので、誰が呼んだかが分かります。
  • .c.c の行番号：各文の前に #line N "withdraw.c.c" を出すので、source_location は C++ ではなく .c.c の行を指します。
  • 値の表示：条件に出てくる変数・フィールド・old(...) を拾い、違反したときだけ repr() で文字列にします。
  • effects に throw がないので noexcept が付いています。

5. ステップ3：スキーマ

schema 1つから、構造体、parse()、to_json() を生成します。

入力 examples/user.c.c

type Email = string matches email_format;

schema Address {
  city: string where len(self) >= 1;
  zip:  string where len(self) == 7;
}

schema User {
  id:      u64         where self > 0;
  name:    string      where 1 <= len(self) <= 50 transform trim;
  email:   Email;
  age:     int?        where 0 <= self <= 150;
  tags:    vec<string> where len(self) <= 3 = [];
  address: Address?;

  invariant(age == none || age >= 13, "13歳以上");
}

フィールドの型

where / matches の付いたフィールドは、入れ子の条件付き型（User::id_t など）になります。そのため構造体に入っている値は、常に条件を満たしています。

  id_t id;
  name_t name;
  Email email;
  std::optional<age_t> age;
  tags_t tags;
  std::optional<Address> address;

6. ステップ4：効果と静的検査

関数が呼ぶもの（関数・?・cpp ブロック）が必要とする効果は、その関数が effects(...) で宣言した効果に含まれていなければなりません。検査はトランスパイル時に行い、C++ には noexcept の有無として残るだけです。

// Pure apart from throwing: no io here, guaranteed by the signature.
fn parse_config(string text) -> Config effects(throw) {
  return Config::parse(parse_json(text))?;
}

fn load_config(string path) -> Config effects(io, throw) {
  return parse_config(read_file(path));
}
呼ぶもの必要な効果
effects を宣言した関数・組み込み関数・extern fn宣言された効果
T::parse / T::try_from（生成されたもの）なし（純粋）
?throw（失敗すると cc::Failure を送出する）
effects を省略した関数、宣言のない C++ 関数、関数内の cpp { }unsafe（中身が分からないため）
メソッド呼び出し x.f()試作では追跡しない

where / pre / post / invariant の条件と既定値は、純粋でなければなりません。

8. 決めたことと制限

effects を省略した関数（CONCEPT.md 未決事項1）：検査せず「何でも可」としました。ただし、効果を宣言した関数から呼ぶには unsafe が必要です。既存コードに少しずつ注釈を足していけます。

既存 C++ の効果（未決事項2）：宣言のない C++ 関数は unsafe 扱いです。extern fn f(...) effects(...); で効果を絞れます。

契約の実行時チェック（未決事項6）：g++ 13 / clang 18 が C++26 Contracts に未対応なので、自前の cc::violation を使っています。

スキーマのエラー（未決事項3）：最初からフィールドのパス付きの構造化データにしました。

既知の制限

  • 対応コンパイラは g++ 13 以降です。clang 18 は libstdc++ 13 の std::expected を使えません。
  • スキーマに enum はありません。スキーマ型の値を作る手段は parse か、cpp / extern fn だけです。
  • メソッド呼び出しの効果は追跡していません。
  • matches / transform に使えるのは、組み込み関数か extern fn だけです。
  • 型推論は最小限です。型が分からない式の誤りは、C++ コンパイラのエラーとして出ます（#line により .c.c の行を指します）。
  • 未着手：with によるハンドラ差し替え、test ブロック、JSON Schema 出力、Z3 による静的証明、所有と手順（once / fixed / protocol）。

## 結論

次に優先するのは型検査の拡充。型検査を広げれば、C++ の文面のエラーの大半と型推論の弱さが同時に解消する。`v[i]` の範囲検査、`ccc run` / `ccc test` のサニタイザ、C++ エラーの要約は実装した。

## 優先度の高いもの

| 制限 | 改善策 | 工数 |
|---|---|---|
| 整数オーバーフローの報告の質、`ccc build` の出力での検出 | `__builtin_add_overflow` を使う演算に変換する | 中 |
| C++ の文面のエラー、弱い型推論 | 式全体に型を付ける型検査を入れ、`.c.c` の位置でエラーを出す。効果を宣言した関数では「型が不明」もエラーにする | 大 |
| `T::parse` の結果の型を書けない | `Result<T, E>` と `ok(...)`、`err(...)` を追加する。`Result` を返す関数の中の `?` は、例外ではなく `err` を返すようにする | 中 |

## 比較的すぐ直せるもの

| 制限 | 改善策 | 工数 |
|---|---|---|
| `try` が `std::exception` しか捕まえない | `catch (...)` も生成し、「不明な例外」というメッセージで受け取る | 小 |
| `enum` を `match` できない | `match role { admin {…} member {…} }` を追加し、分岐の漏れをエラーにする | 小 |
| 既定値の検査が `parse` 時になる | `where` は式を絞ったので、リテラルなら `ccc` 自身が評価してコンパイルエラーにできる。`matches` は起動時に一度だけ検査し、「スキーマの既定値が不正」と報告する | 小〜中 |
| `matches` と `transform` に C.C. の関数を使えない | `invariant` と同じように、本体を関数の宣言より後に出力する | 小 |
| テストの絞り込みができない | `ccc test file -- 名前` と、ディレクトリ単位の実行を追加する | 小 |

## 設計の判断が要るもの

| 制限 | 改善策 | 工数 |
|---|---|---|
| `with` で `read_file` しか差し替えられない | ハンドラに `print`、`eprint`、ファイル書き込みを足し、出力を検証できる `Capture` を用意する。`with` は `test` 専用のままにする | 中 |
| スキーマ型の値を `parse` でしか作れない | `Server::make(name: "a", listen: 80)?` のように、同じ検査を通して `Result` を返す構文を追加する。`Result` の型を先に入れる必要がある | 中 |
| `ccc test` が POSIX 専用 | `fork` の代わりに、自分自身をテストごとに起動し直す方式にする。Windows を対象にするまでは急がない | 中 |
| `extern fn` の効果を検証できない | C++ の中身は検証できないので、完全には解決しない。信頼している箇所を一覧にする `ccc audit` を作り、`extern fn` にも `pre` / `post` を書けるようにして、実行時に検査できる範囲を広げる | 中 |

## 進める順序

1. **安全性:** `catch (...)`（`v[i]` のチェックとサニタイザは実装済み）
2. **言語の仕上げ:** `enum` の `match`、既定値の静的検査、`matches` の拡張、テストの絞り込み
3. **`Result<T, E>`:** スキーマ型の値を作る構文も、これに続けて入れる
4. **型検査の拡充:** 最も大きい作業。フェーズ3の Z3 連携は式の型が分かっているほうが作りやすいので、Z3 より先に済ませる
5. **`with` の拡張と `ccc audit`:** 実際のプログラムで必要になった時点で着手する
